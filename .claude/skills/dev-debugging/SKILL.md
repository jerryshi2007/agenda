# dev-debugging · 系统化调试

## 铁律

```
无根因调查不提议修复
```

随机修复浪费时间、制造新 bug。快速补丁掩盖底层问题。

## 何时使用

- 测试失败
- 生产环境 bug
- 异常行为
- 性能问题
- 构建失败

## 四阶段法

必须按顺序完成每个阶段，不可跳过。

### Phase 1: 根因调查

1. **完整读错误信息**——不跳过任何 warning 或 error，完整读堆栈
2. **稳定复现**——确定触发条件、是否每次必现
3. **检查最近变更**——git diff、最近提交、新依赖、配置变更
4. **多组件系统收集证据**——在每个组件边界处加诊断日志，确认数据在哪一层开始出错
5. **追踪数据流**——坏值从哪来？谁调用了产生坏值的代码？一路追溯到源头

### Phase 2: 模式分析

1. **找工作示例**——在同一个代码库中找到类似且正常工作的代码
2. **对比参考**——完整阅读参考实现，不跳读
3. **识别差异**——列出所有差异，不假设"这不重要"
4. **理解依赖**——这个组件需要什么其他组件、配置、环境？

### Phase 3: 假设与测试

1. **形成单一假设**——清晰表述"我认为 X 是根因，因为 Y"
2. **最小测试**——用最小改动验证假设，一次只改一个变量
3. **验证**——通过→Phase 4；不通过→新假设
4. **不知道就说不知道**——不要假装理解

### Phase 4: 实现

1. **创建失败测试**——最小复现脚本或自动化测试
2. **单一修复**——一次只改一个地方，不夹带重构
3. **验证修复**——测试通过？无回归？
4. **如果修复无效**——计数。如果已尝试 2+ 次修复失败，返回 Phase 1 重新分析
5. **如果 3+ 次修复都失败**——质疑架构。这不是假设错误，这是架构问题。和用户讨论。

## Red Flags——STOP 并返回 Phase 1

- "快速修一下，之后再调查"
- "试试改 X 看看效果"
- "同时改多处，一起跑测试"
- "不写测试了，手动验证"
- "我大概知道问题在哪，直接修"
- "再来一次修复尝试"（已经试了 2+ 次）
- 每次修复暴露不同地方的新问题
- 提解决方案之前没追踪数据流

## 关键原则

- 复现优先——不能复现就别改。
- 一次一个假设——多假设并行会混淆因果。
- 修根因——吞症状的 bug 会在更糟的时候回来。
- 3+ 次修复失败 = 架构问题，不是调试问题。
