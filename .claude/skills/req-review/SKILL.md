# req-review · 需求审核

## 在流程中的位置

`openspec-propose` → **req-review**（需求审核）→ 人审批 → `dev-planning`（任务分解）

## 何时使用
- 审批 OpenSpec proposal + delta spec 时
- 多个并行 proposal 需要联合审核时
- 需求质量存在疑虑，需要系统化审查时

跳过场景：简单 bug 修复、格式调整、文档更新等平凡变更（无需 proposal 的豁免场景）。

## 流程

1. **先 Read `rules/req-spec.md` 和 `rules/openspec-workflow.md` 并严格遵守其约束。**

2. **理解变更意图**
   - 读 `openspec/changes/<name>/proposal.md`：变更动机、范围、影响分析
   - 读 `openspec/changes/<name>/specs/*/spec.md`（delta spec）：ADDED / MODIFIED / REMOVED 的 Requirements + Scenarios
   - 搞清楚：这次变更要解决什么问题？改了哪些已有需求？新增了什么需求？

3. **对比现状 spec**
   - 读 `openspec/specs/<domain>/spec.md`（当前真相源）
   - 逐条对照 delta 与现状：
     - MODIFIED 需求：delta 是否与现状有矛盾？修改后是否丢失了现状的有效约束？
     - ADDED 需求：是否与已有 spec 中其他 domain 的需求冲突？
     - REMOVED 需求：删除是否有明确理由？是否有其他模块依赖此需求？
   - 特别关注：两个不同 domain 的 spec 对同一概念的描述是否一致

4. **跨变更一致性检查**（多 proposal 联合审核时）
   - 两个（或多个）并行 proposal 之间的互相引用是否正确？
   - 是否存在矛盾——如 proposal A 的 MODIFIED 与 proposal B 的 ADDED 冲突？
   - 是否存在遗漏——如 proposal A 的影响分析提到了 B 模块，但 proposal B 未做对应处理？
   - 是否有共享概念定义不一致——如同一术语在两个 delta 中定义不同？

5. **按 10 维度扫描**

   | # | 维度 | 检查内容 | 严重度 |
   |---|------|---------|--------|
   | 1 | 动机合理性 | 变更动机是否清晰？要解决的真实问题是否明确？是否能用 2-3 句话说清"为什么现在要做这个变更"？ | 阻塞 |
   | 2 | 范围完整性 | 变更范围是否覆盖所有受影响模块？proposal 的影响分析是否遗漏了关联模块？ | 阻塞 |
   | 3 | 需求可验证性 | 每条 Requirement 能否用"通过/未通过"判定？是否有模糊词（"快""足够""友好""安全""可靠"）未量化？ | 阻塞 |
   | 4 | 场景覆盖 | 每个 Requirement 是否至少有 1 个正常路径 Scenario + 1 个异常路径 Scenario？ | 阻塞 |
   | 5 | 边界与异常 | 空值、越界、并发、失败回退、权限不足等边界场景是否覆盖充分？ | 建议 |
   | 6 | 现状兼容性 | Delta spec 与已有 `openspec/specs/` 是否冲突？是否引入矛盾？是否有概念定义不一致？ | 阻塞 |
   | 7 | 跨变更一致性 | 多个并行 proposal 之间的引用是否正确？是否有矛盾或遗漏？（单 proposal 时跳过） | 建议 |
   | 8 | 影响分析完整性 | 对关联模块、数据模型、鉴权链路的影响是否识别完整？是否有"影响分析"未提及但实际会受影响的模块？ | 建议 |
   | 9 | 优先级合理性 | Requirements 的 Must/Should/Could 分级是否合理？是否有明显的优先级错配？ | 建议 |
   | 10 | RFC 2119 合规 | MUST/SHALL（绝对要求）、SHOULD（推荐）、MAY（可选）使用是否正确？约束强度是否恰当？ | 建议 |

6. **列发现**
   - 每条发现记录：所属维度、具体位置（文件名 + Requirement 名 + Scenario 名）、问题描述、为什么是问题

7. **逐条验证**
   - 对每条发现反问"这真的会导致验收失败或实现返工吗？"
   - 排除误报——可商榷的风格偏好不算问题
   - 确认阻塞项确实阻塞审批（不澄清就无法判断审批是否通过）

8. **按严重度排序**
   - **阻塞**：审批前必须澄清或修复（如需求不可验证、与现状 spec 冲突、场景缺失）
   - **建议**：审批前建议关注（如边界覆盖不足、优先级可疑）
   - **疑问**：需审批人确认的事项（如"这个设计选择是否正确？"）

9. **给审批建议**
   - 用 AskUserQuestion 逐条追问阻塞和疑问项，不假设答案
   - 收集澄清结果后，给出三判决：
     - **需求质量**：✅ 合格 / ⚠️ 有保留 / ❌ 不合格
     - **现状兼容性**：✅ 兼容 / ❌ 存在冲突
     - **审批建议**：✅ 建议批准 / ⚠️ 建议有条件批准 / ❌ 建议驳回

10. **输出审核报告**
    - 写入 `openspec/changes/<name>/review.md`
    - 联合审核时，跨变更一致性检查结果也写入报告
    - 报告模板：

    ```markdown
    ## 审核报告: <change-name>

    > 审核日期：YYYY-MM-DD
    > 审核范围：proposal.md + delta spec.md（+ 联合审核: <其他 change 名>）

    ### 1. 总览

    | # | 维度 | 结果 | 问题数 |
    |---|------|------|--------|
    | 1 | 动机合理性 | ✅ | 0 |
    | 2 | 范围完整性 | ✅ | 0 |
    | 3 | 需求可验证性 | ✅ | 0 |
    | 4 | 场景覆盖 | ✅ | 0 |
    | 5 | 边界与异常 | ⚠️ | 2 |
    | 6 | 现状兼容性 | ✅ | 0 |
    | 7 | 跨变更一致性 | ⚠️ | 1 |
    | 8 | 影响分析完整性 | ✅ | 0 |
    | 9 | 优先级合理性 | ✅ | 0 |
    | 10 | RFC 2119 合规 | ✅ | 0 |

    ### 2. 问题清单

    #### 阻塞（审批前必须澄清）
    | # | 维度 | 位置 | 问题 | 建议 |
    |---|------|------|------|------|

    #### 建议（审批前建议关注）
    | # | 维度 | 位置 | 问题 | 建议 |
    |---|------|------|------|------|

    #### 疑问（需审批人确认）
    | # | 维度 | 位置 | 问题 | 选项 |
    |---|------|------|------|------|

    ### 3. 审核判决

    | 判决 | 结果 |
    |------|------|
    | 需求质量 | ✅ / ⚠️ / ❌ |
    | 现状兼容性 | ✅ / ❌ |
    | 审批建议 | ✅ 建议批准 / ⚠️ 建议有条件批准 / ❌ 建议驳回 |

    ### 4. 待澄清问题及结果

    [AskUserQuestion 收集到的澄清内容]

    ### 5. 审核备注

    [其他值得审批人注意的事项]
    ```

## 关键原则

- **不代替人审批**——给出建议，标注置信度，最终决策由人做出
- **先验证再下结论**——可疑不等于有问题，每条发现必须能说出"这为什么会导致问题"
- **报真问题，不为凑数**——假问题淹没真问题，降低审核报告可信度
- **严重度区分严格**——阻塞 = 审批前必须解决；建议 = 值得关注但可先通过；疑问 = 需人确认
- **对比现状 spec**——不只看 delta 本身，必须对照 `openspec/specs/` 检查兼容性
- **跨变更视角**——多 proposal 联审时，矛盾和不一致是最高价值的发现
- **可执行**——每条建议必须能直接操作（具体改哪里、怎么改）
