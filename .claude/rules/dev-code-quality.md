# dev-code-quality · 代码质量底线

## 约束

- **命名表意图**——变量/函数/类型名能说明"是什么"和"做什么"，无需注释解释。命名不清是设计不清的信号。
- **单一职责**——一个函数/类/模块只做一件事。混合多职责的代码改动牵一发动全身。
- **YAGNI**——只实现当前需要的，不为臆想的未来需求加抽象/扩展点。三分相似代码优于过早抽象。
- **不写无用注释**——注释只解释"为什么"（隐藏约束、绕过 bug、反直觉行为），不复述"做什么"（代码已说明）。
- **错误处理只在边界**——系统边界（用户输入、外部 API、IO）校验并处理；内部代码信任约定，不重复防御。**边界处捕获的异常必须处理**（日志 + 降级 + 重试，不吞异常不空 catch，具体规范见 `dev-dotnet-standards` 异常处理节）。
- **优先复用已有实现**——动手前先查是否有现成工具/函数。重复实现是技术债。
- **无占位符原则**——实现计划中禁止出现 TBD、TODO、"后续补充"、"类似 Task N"等占位描述。每个步骤必须包含实际代码或具体指令。

## 示例

- ✅ `function findActiveUser(users) { return users.find(u => u.isActive); }`（命名清楚、单一职责）
- ❌ `function processStuff(data, flag, opts) { /* 处理数据 */ /* flag 时也校验 */ /* 还要格式化 */ }`（职责混杂、命名含糊）
- ❌ 为"以后可能支持多种格式"提前抽象出 `FormatterFactory`，实际只有一种格式
